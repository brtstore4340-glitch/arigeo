## Honest Feedback (Friction Points)

**Friction Point 1: NTFS Mount Performance on Large Directories**
The 1.5GB arra directory timeout revealed that recursive file operations on WSL2-mounted NTFS are much slower than on native Linux filesystems. This isn't a bug; it's environmental. But it means any future cleanup of large oracle memory directories needs to budget 15+ minutes per 1GB and should run async, not inline.
**Severity**: Moderate. Blocking for this session, but not a blocking issue for the overall fleet.
**Workaround**: Schedule node_modules cleanup as a separate async job, not part of the critical audit path.

**Friction Point 2: Git Submodule Lock Contention**
The aeimathes-oracle directory contained a broken git worktree reference (`agent-a446a9285982f1cb7`), which blocked *all* git operations on the parent repo. This happened because a background session created an isolated worktree that wasn't cleaned up properly.
**Severity**: High. Completely blocked the commit.
**Root cause**: Orphaned worktree from a prior background job. The harness should have cleaned it up, or we should have explicit cleanup on exit.
**Workaround**: Remove the submodule reference, allow re-adding it later.

**Friction Point 3: File Creation in Bash Script Vs. Actual Disk**
When I ran the Priority 2 bash script, it claimed to create `fleet-registry/memory/zeus/CLAUDE.md` and others. But after the script exited, those files didn't exist on disk. The script's file writes weren't persisting.
**Severity**: Moderate. Required manual file creation afterward, but all data is correct now.
**Root cause**: Unclear. Possibly the script ran in a subshell with a different working directory, or the paths weren't resolved correctly.
**Lesson**: Always verify file creation with `ls` immediately after the script, don't assume.

## Lessons Learned (Generalizable Rules)

**Lesson 1: Audit Before Migration**
When dealing with scattered or fragmented data (oracle memories, configurations, contexts), always audit the current state before attempting migration. This audit should identify:
- What exists where (current distribution)
- What's missing (gaps in the manifest)
- What's extra (unregistered items)
- Data integrity (are critical files present)

Then present findings to stakeholders before proceeding. In this case, the audit revealed that 8 extra oracles exist outside the registry — critical information that would have been lost in a blind migration.

**Lesson 2: Decouple Critical Path from Optimization**
When facing multiple priorities with different risk profiles, separate them:
- **Critical path**: Restore identities, fix registrations, ensure no data loss. Must complete this session.
- **Optimization**: Clean up bloat, remove large artifacts. Can be deferred and run async.

Mixing them causes the whole pipeline to fail if the slow part times out. Separate them = both can proceed in parallel without blocking.

**Lesson 3: WSL2 NTFS Mount Operations Are Slow at Scale**
Recursive operations (find, rm, rsync) on large directory trees via WSL2→NTFS mount are 10-100× slower than native Linux. Budget accordingly:
- < 10MB: instant
- 10MB-100MB: seconds to minutes
- 100MB-1GB: minutes to 10 min
- > 1GB: 15+ min (risky to include inline)

Use `du -sh` for quick estimates before deciding to run inline vs. async.

**Lesson 4: Document the Extra/Unregistered Oracles Explicitly**
The 8 extra oracles (aeimathes, arra, codex, hermes, khun-ram, opensource-nat-brain, uat, unknown-oracle) are legitimate artifacts with data. Rather than deleting them or ignoring them, document them in the audit with:
- Name
- Size
- Location in registry
- Recommendation (register, investigate, keep as-is)

This creates an explicit backlog for Phase 3, rather than leaving them as a nagging loose end.
