## Lessons Learned

- **Testing a hook's own script logic is not the same as testing whether the hook fires.** Manually exporting env vars and running the command directly only proves the script is correct in isolation — it says nothing about whether the actual hook-runner wires it up right. Use the real invocation path (e.g. `claude -p --debug hooks` for Claude Code hooks) before reporting something as confirmed.
- **Hook `matcher` fields exact-match tool names only.** The `Tool(pattern)` parenthetical syntax from permission `allow`/`deny` rules does not carry over to hook matchers for filtering by tool-input arguments (confirmed for the `Skill` tool). To filter by an argument, match the bare tool name and do the filtering inside the hook command itself, reading the tool's stdin JSON.
- **Don't assume common CLI tools are installed in the target execution environment.** Verify with `which` before depending on something like `jq` in a script that will run inside a hook or automated pipeline — a missing dependency in a hook that matches broadly can silently break every invocation of that tool, which is worse than the original bug.
- **When adjacent directories are owned by different system users, operate as the actual owner** (`su - <user> -c "..."`) rather than reaching for a global git/system config change to work around an ownership mismatch — keeps git identity and config scoped correctly and avoids touching shared state you don't need to.
