## Architecture Decisions & Rationale

### 1. **NDJSON Over Markdown/Database**

**Choice**: Append-only Newline-Delimited JSON at `ψ/fleet/BROADCAST-LOG.ndjson`

**Why**: 
- Git-native (no merge conflicts on append)
- Queryable with jq (no custom parsers)
- Offline-safe (no external dependencies)
- Human-readable (text format, one event per line)

**Tradeoff**: No real-time distributed sync (solved by periodic git pulls; acceptable for 3 oracles on same filesystem).

### 2. **Hook-Based Automation Over Manual Polling**

**Choice**: SessionStart hook + git post-commit hook for automatic emission

**Why**:
- Zero-friction (events emit without user intervention)
- Captures intent at source (not reconstructed later)
- Scales to 100+ oracles without polling overhead

**Tradeoff**: Depends on Claude Code hook system and git hooks (both proven, low-risk).

### 3. **Phase 1 Foundation First, Phase 2 Hooks Later**

**Choice**: Separate into 2 phases (foundation + automation) instead of full system in 1 phase

**Why**:
- Phase 1 proves the storage format + API works before adding hooks
- Easier to debug if hooks fail (know the core system works)
- Allows manual testing (emit, query, dashboard) before automation

**Tradeoff**: More commits (6 instead of 3) but much clearer git history for audit.

### 4. **Dashboard as Bash + jq, Not a Full Server**

**Choice**: fleet-dashboard.sh (CLI script) instead of HTTP server or web UI

**Why**:
- Zero external dependencies
- Runs anywhere (any machine with bash + jq)
- Can be integrated into cron jobs, alerts, or CI/CD
- Fast (grep-based queries for non-jq fallback)

**Tradeoff**: No real-time web UI (solved by running dashboard on demand; can add Grafana integration later).

### 5. **Same System for All 3 Oracles (No Customization)**

**Choice**: Deployed identical system to Zeus, Luxi, Tham

**Why**:
- Consistency across fleet
- All oracles speak same "broadcast language"
- No surprises when fleet expands to 10+ oracles

**Tradeoff**: Each oracle has identical BROADCAST-LOG.ndjson (not unified). Later enhancement: shared broadcast log via symlink or git submodule (not needed yet).

## Honest Feedback

**Friction 1 — Gitignore Exception Syntax**: First attempt to add `!/scripts/fleet-*.sh` to .gitignore failed. The order of exceptions vs. exclusions matters in gitignore (exception must come BEFORE the exclusion). Took 2 attempts to fix. Lesson: gitignore rule ordering is non-obvious; document this if we use patterns elsewhere.

**Friction 2 — Settings.json Creation**: Luxi didn't have a .claude/settings.json file, so I had to create it from scratch. This worked fine, but exposed that not all oracles have identical config structure. If we scale to 10 oracles with different setups, syncing config changes becomes a pain point.

**Friction 3 — Phase 2 Deployment Manual Replication**: Copying fleet-emit.sh and fleet-dashboard.sh to Luxi and Tham was manual (bash cp commands). With 10+ oracles, this scales poorly. Future: create a deployment script that replicates fleet infrastructure to all oracles at once.

## Lessons Learned

**1. Append-Only Logs Beat Databases for Fleet Coordination** — When all you need is "what happened when," git-tracked append-only NDJSON is simpler and more auditable than a database. No concurrency issues, no external dependencies, audit trail is in git history. Apply this: any audit-heavy feature (deployment log, decision record, incident timeline) should default to append-only JSON over database.

**2. Separate Foundation Phase from Automation Phase** — When deploying a new system across multiple instances, separate the foundation (does it work?) from automation (does it scale?). Phase 1 proved the core works (4 test events, dashboard summary verified). Phase 2 added hooks with confidence. This pattern saves debugging time.

**3. Hooks Reduce Friction But Increase Brittleness** — SessionStart hook now emits automatically, which is great for UX. But if the hook fails silently (e.g., fleet-emit.sh not found), users won't know events aren't being broadcast. Add hook validation (post-SessionStart: verify BROADCAST-LOG was updated) or at least log errors visibly.

**4. Configuration Should Be Self-Discovering** — Hardcoding oracle name in git hooks works for 3 oracles. At 50 oracles, it's unmaintainable. Better: read oracle identity from CLAUDE.md at runtime. Lesson: for any fleet-wide feature, config should flow from a single source of truth (CLAUDE.md), not be duplicated in multiple places.
