## Architecture Decisions & Rationale

### 1. **Tier-Based Budget Enforcement (vs. Binary Allow/Disallow)**

**Choice**: 4-tier system (Green/Yellow/Red/Critical) with automatic strategy shifts.

**Why**: Binary rules (e.g., "never re-read") are brittle — edge cases abound. Tiered lets agents adjust strategy gracefully as budget tightens, scaling from "normal iteration" → "surgical reads" → "direct answers only" → "stop and wrap." No permission prompts; automatic.

**Tradeoff**: Requires clear tier detection (solved via token %). Less rigid than hard bans, but more aligned with real budget dynamics.

### 2. **Cache as JSON File (vs. Redis/External)**

**Choice**: File-based L1 cache (cache.json), 1-hour TTL, auto-managed.

**Why**: Zero external dependencies. Auto-created. Auto-invalidates on git changes or session boundary. Simple, reliable, works offline.

**Tradeoff**: Single-file (not shared fleet-wide). Sufficient for this scale; Redis upgrade is documented as future enhancement.

### 3. **Worktree for Isolation (vs. Branching + Rebasing)**

**Choice**: `/worktree` isolates large changes into separate directory + branch, prevents context pollution.

**Why**: Each iteration in a worktree sees only its own diff (clean, small). Main session context stays untouched. Easy merge/rollback. ~1500 tokens saved per 10-iteration refactor.

**Tradeoff**: Requires discipline (cleanup with `git worktree prune`). Worth it for >100-line changes.

### 4. **Systematic Memory Rules (vs. Free-Form Notes)**

**Choice**: Structured MEMORY-RULES.md: type/TTL/load discipline for each memory class.

**Why**: Without rules, vault decays (old unused facts accumulate). With rules, vault stays fresh and useful. Write once, reuse forever — zero re-derivation.

**Tradeoff**: Requires upfront planning (which type? what TTL?). Verified by checklist before saving. High payoff.

### 5. **Same System for All 3 Oracles (vs. Oracle-Specific Variants)**

**Choice**: Deploy identical context budget rules, memory system, cache setup to Zeus, Luxi, Tham.

**Why**: Consistency across fleet. All agents speak same "tier language." No confusion. All benefit from same token savings.

**Tradeoff**: Luxi (UI/UX focus) and Tham (orchestration focus) might want domain-specific tweaks later. Easy to customize CLAUDE.md per oracle while keeping ψ/memory system standard.

## Lessons Learned

**1. Read all contexts before designing-for-all.** When deploying a system across multiple oracles, read all CLAUDE.md files upfront to understand differences (branch names, gitignore patterns, existing related sections). Design once for all variants, then implement. Avoid "iterate on one, adapt to others" — it causes rework and inconsistency drift.

**2. Gitignore patterns aren't standardized across oracle repos.** Zeus/Tham exclude /ψ/ (vault is external/shared); Luxi doesn't have that pattern. Document fleet-wide gitignore convention so new oracles don't diverge. Current state is inconsistent — some repos will track memory, others won't, creating confusion.

**3. Cache creation should be defensive.** Auto-created resources (cache.json, project dirs) should explicitly create parent directories and handle missing state gracefully. Don't assume ~/.claude/projects/<encoded>/ exists. This is operational hardening, not a bug fix — the system works, but robustness needs shoring up.

**4. Documentation (TOKEN-OPTIMIZATION-GUIDE.md) should ship with system, not after.** I wrote it last as a summary. Better approach: write guide first (forces clear thinking), then implement from guide. The guide became a spec retrospectively, which is backwards. Next system deploy: guide-first.

**5. Parallel oracle updates require verification script.** I verified all 3 oracles by hand (checking each cache.json, each ψ/memory/ dir). Better: one script that checks all 3 repos at once. Scales to 10+ oracles without manual checklist fatigue.
