## Lessons Learned (Generalizable Rules)

### Lesson 1: Specification as Deliverable
> **Rule**: Detailed specifications (PRODUCT + DESIGN + WIREFRAMES) are themselves done-work. Don't undervalue them because they're not "shipped code." A well-specified project can be implemented 3x faster than a vague one.

**Why**: This session designed 2 projects (Pharmacy, Web Hosting) from scratch to delegation-ready in ~4 hours. Luxi will now build Figma mocks without ambiguity. vs. typical flow where she'd spend hours clarifying.

**Apply**: When scoping design work, count specifications as deliverables (estimate 4-6 hours per project end-to-end). Don't treat them as "prep work."

---

### Lesson 2: Template-Driven Design Enables Speed
> **Rule**: Create PRODUCT/DESIGN/WIREFRAMES templates once (e.g., pharmacy medical). Reuse them for other projects with customization (e.g., web hosting tech colors). 3-5 hours per complete project instead of 10+ hours from scratch.

**Why**: Second project (Web Hosting) went faster than first (Pharmacy) because I had templates. Wireframes used same 5-screen pattern; design system used same token structure.

**Apply**: Build reusable templates for projects in same category (healthcare, SaaS, IoT). Share across team.

---

### Lesson 3: Risk Classification Drives Security Design
> **Rule**: Security gating (approval workflows, audit trails) should be classified by risk level (read/low/medium/high/critical). Don't gold-plate all operations; gate proportionally.

**Why**: LINE integration spec identified read operations (no approval) vs. production deploys (require approval). This prevented over-engineering (would've required approval for /status) and under-engineering (forgot critical-risk 2FA).

**Apply**: When designing API/command/workflow, create risk matrix first. Then gate accordingly.

---

### Lesson 4: Delegation Requires Specification, Not Permission
> **Rule**: Don't ask "Can you do X?" — just spec "Here's X, these are success criteria, here's the timeline." Designers/developers respect clarity over permission requests.

**Why**: Luxi didn't need me to ask. I sent detailed task orders (Figma mockups spec, Storybook components spec, acceptance criteria). She can now proceed or push back on ETA.

**Apply**: Write task orders like contracts, not requests. Clear acceptance criteria = clear boundaries.
