## Honest Feedback
1. **Session-detection broke on spaces in the workspace path.** The /rrr skill's `sed 's|[/.]|-|g'` doesn't convert spaces, so the encoded project dir didn't match and `SESSION_ID` came back `unknown` until I located the `.jsonl` manually. Cost extra bash round-trips.
2. **`maw wake` launched claude in `/route/mission-control`, not the oracle's own repo.** Despite `maw locate` resolving the correct repo, both wakes booted the mission-control project/picker (FleetView showed *my* jobs). A path-resolution bug in the wake flow blocked clean interactive delivery.
3. **No-TTY background job can't `-a` attach.** `tmux attach-session` errored (status 1) from the tool context. Waking an oracle interactively is fundamentally a human-with-terminal action, and I burned a cycle confirming the predictable.

## Lessons Learned
- Before asserting a deliverable is missing, resolve the *canonical* source (`maw locate <oracle>` / registry) and search THAT — an in-tree submodule or mirror may be stale. Never conclude "doesn't exist" from a partial search.
- Oracle outbox notes do not auto-relay between agents; a "completed" deliverable can sit unread for days. When asked for another agent's status, check its `ψ/outbox` in the canonical repo first.
- `maw wake -a` cannot attach from a non-interactive/background agent (no TTY). When delivery needs an interactive boot, write the durable `ψ/inbox/` file (read on RTK) and hand the attach to the human — don't retry the wake.
