## Session Summary

User reported that tg-relay caused an incorrect `tmux kill-window` — a window that should not have been touched got destroyed. The ask was: (1) cancel the kill-window behavior, (2) disable tg-relay entirely for now.

Root cause identified: `tg-relay.sh` built a command string with `tmux kill-window` but without an explicit `-t` target. When the shell executes inside the temp window, tmux kills whichever window is "current" in that context — which can be any window in the session, including zeus-oracle.

Three actions taken:
1. Fixed `tg-relay.sh` — added `-t '${ZEUS_SESSION}:${WIN_NAME}'` to be precise
2. Disabled the Stop hook in `.claude/settings.json` — set `"Stop": []`
3. Killed orphan relay window `10-zeus:0` (tg-relay-1170-)

During cleanup, a race condition hit: the Stop hook fired one more time (pid=26992) before settings.json change propagated. The old in-flight invocation ran `tmux kill-window` without a target — and killed the entire `10-zeus` session, destroying zeus-oracle.

Recovered by running `maw wake zeus`. Final state confirmed: all 4 sessions intact (`03-tham`, `10-zeus:zeus-oracle`, `11-khun-ram`, `17-aeimathes`).

When I found the orphan relay window `10-zeus:0`, I killed it immediately after disabling the Stop hook. That action — killing the window while a Stop hook invocation was still in-flight — is what triggered the race condition. At that moment, the previous session had already ended, the relay had started running as an async background process, and the in-flight process (pid=26992) was mid-execution with the *old* code (before my fix had been applied to it). ## Honest Feedback

**3 friction points specific to this session:**

1. **No async hook drain mechanism**: Disabling `"Stop": []` in settings.json prevents *future* hook firings but has zero effect on hooks already running (`async: true`). There's no built-in "drain" command. The only safe method is `pkill -f tg-relay.sh` or checking `pgrep -f tg-relay.sh` before doing window cleanup. This gap is a platform limitation but I should have worked around it.

2. **No visibility into in-flight async hooks**: Claude Code doesn't surface which async Stop hooks are currently executing. I had to infer it post-hoc from the log showing pid=26992. If the log hadn't shown that PID, I wouldn't have known a second relay was in flight. A pre-cleanup `pgrep` check should be standard procedure.

3. **Context compaction compressed the earlier investigation**: The session continued from a prior context window that had compacted. Some of the investigative steps (reading tg-full.sh, checking both settings.json paths) are summarized in the handoff, so the retro timeline above interpolates slightly between known timestamps. Real timestamps from dig-miner show only 2 user messages in the session (21:48 and 22:43) — the entire fix happened between those two points.

## Lessons Learned

1. **Async Stop hooks are independent processes — disable ≠ drain.** Setting `"Stop": []` prevents future firings but any in-flight async process continues to completion. Check `pgrep -f <hook-script>` and wait for it to exit before touching shared resources (tmux windows, files) that the hook accesses.

2. **`tmux kill-window` without `-t` is a footgun in any script that runs inside tmux.** The "current" window in script context is unpredictable, especially when spawned via `tmux send-keys`. Always use explicit `-t session:window` targeting when self-destructing.

3. **Safe cleanup order for tmux-spawned hook scripts: fix → disable trigger → drain in-flight (`pgrep` + wait or pkill) → clean up resources.** Never clean up shared resources while in-flight processes may still reference them.
