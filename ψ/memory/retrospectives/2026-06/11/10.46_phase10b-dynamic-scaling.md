## Architecture Decisions

1. **Separation of Concerns**: 5 distinct components rather than monolithic scaler
   - Rationale: Testability, reusability, clear responsibilities

2. **EventEmitter pattern**: MetricsCollector → ScalingPolicy → DynamicScaler
   - Rationale: Loose coupling, reactive (not polling-heavy)

3. **Generation-based recovery**: Lease management with version tracking (from Phase 6)
   - Rationale: Prevents split-brain, enables safe failover

4. **Cost cap enforcement**: Required by design, enforced at policy level
   - Rationale: Operational constraint — prevent runaway scaling

5. **Polling interval (10s)**: Trade-off between responsiveness + overhead
   - Rationale: Sub-second decisions unnecessary; 10s catches Q buildup

## Lessons Learned

**Lesson 1: Governor Acts When Chain Breaks**
- **Rule**: When agent delegation exceeds 10s with no response, Governor (Zeus) executes directly instead of waiting.
- **Why**: Delegation overhead (tmux dispatch, inbox messages, agent initialization) can exceed direct execution time for tasks <2h of work.
- **How to apply**: Set internal timeout on `maw dispatch` calls. If timeout exceeded, `echo "Agent busy — executing directly"` and implement.

**Lesson 2: Threshold-Based Scaling Needs Hysteresis**
- **Rule**: Binary thresholds (Q>15 spawn, Q<3 retire) cause oscillation near boundary. Add hysteresis band (e.g., spawn at 15-18, retire at 3-5).
- **Why**: Queue fluctuates naturally; single point thresholds → flapping.
- **How to apply**: Next phase (10-B v2), add `threshold_hysteresis` parameter to ScalingPolicy.

**Lesson 3: Separate Operational Metrics from Decision Metrics**
- **Rule**: MetricsCollector should emit both raw metrics (for dashboards) AND decision-inputs (for policy). Currently mixed.
- **Why**: Easier testing, clearer data flow, better for debugging scaling behavior.
- **How to apply**: Refactor MetricsCollector to emit `{ raw: {...}, decision: {...} }` tuple.
